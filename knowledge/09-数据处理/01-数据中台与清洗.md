# 数据中台：外部数据 → 清洗 → 推荐 → 线索

> 归属：`crm-data` · docKey：`crm/data/data-center` · 证据：`c_*` 清洗表（25+）/ `t_data_*` 业务表 / `c_recommend_*` + ltc/data（7 控制器 / 53 接口）

## 一句话

数据中心是**线索的上游工厂**：从外部（省实名制、工程款、招投标）抓数据 → 清洗成 `c_*` → 转成业务数据 `t_data_*` → 按规则**推荐给销售** → 销售认领后变成线索。

线索的"**自动化创建**"（`t_clue_business.CREATE_TYPE=2`）就是从这里来的。

## 三条命名线，看懂表名就懂流程

| 前缀 | 含义 | 例 |
|---|---|---|
| `c_*` | **清洗数据**（clean）——外部原始数据落库，字段多、脏 | `c_project_info`、`c_engineering` |
| `t_data_*` | **业务数据**——从清洗表转换来的结构化数据 | `t_data_engineering`、`t_data_project_bidding` |
| `t_*`（无 data） | **业务正式数据**——真正的线索/商机/合同 | `t_clue`、`t_clue_business` |

```
外部系统（省实名制 / 工程款 / 招投标 / ZHGD / YTH）
        ↓ 采集（DataCollectController）
   c_*  清洗表（41~56 字段，保留原始字段）
        ↓ 转换 + 去重合并
   t_data_*  业务数据表
        ↓ 推荐（RecommendRecordController）
   c_recommend_record / _detail / _similarity
        ↓ 销售认领
   t_clue（自动创建，CREATE_TYPE=2）
```

> 关键认知：**数据中心的工程和业务侧工程不是同一张表**。`t_data_engineering` 与 `t_project_info` 之间靠 `DATA_ENGINEERING_ID` / `DATA_PROJECT_MASTER_ID` 关联（`t_project_info` 里就有这两个字段）。

## 七个控制器

| 控制器 | 职责 |
|---|---|
| `DataCollectController` | 数据采集（从外部源拉数据） |
| `DataCleanController` | 清洗（字段映射、格式标准化） |
| `DataStoreController` | 入库、转业务数据 |
| `RecommendRecordController` | **推荐记录**（推荐给谁、认没认） |
| `RecommendAutoAuditController` | 推荐自动审核（符合条件免人工） |
| `ProjectBiddingController` | 招投标专项 |
| `ProjectResourceController` | 工程资源（工程款/保函等） |

## 推荐的落地结构

| 表 | 作用 |
|---|---|
| `c_recommend_record` | 推荐主记录（25 字段）：推荐给谁、状态、来源 |
| `c_recommend_record_detail` | 推荐明细（14 字段） |
| `c_recommend_record_similarity` | **相似数据**（8 字段）——推荐时发现的历史相似工程 |
| `c_recommend_data_source` / `_column` | 推荐字段映射配置 |

`_similarity` 这张小表很关键：推荐前先查"这个工程是不是已经有人跟过"，**撞单预防在上游就做了一次**。

## 工程合并（去重）

`t_data_engineering_merge` + `_detail` + `_subtable` + `_tmp`：外部数据里同一个工地会有多条（不同来源、不同批次录入），合并靠这四张表记录"哪几条并成了一条"。

另外 `c_project_similarity_tmp`（项目对比记录临时表）是相似度计算的中间结果。

## 数据源覆盖

| 来源 | 对应清洗表 | 用途 |
|---|---|---|
| 省实名制 | `c_engineering`、`c_engineering_person_extend`、`c_engineering_builder_license` | 工程 + 人员 + 施工许可 |
| 招投标 | `c_project_bidding` / `_detail` / `_person` | 招标、投标、评标信息 |
| 工程款 | `c_project_performance_payment` / `_file` / `_progress`、`c_guarantee_case` / `_order`、`c_institution` | 履约支付、保函 |
| 合同网签 | `c_project_net_contract` | 谁和谁签了合同 |
| 物联网设备 | `c_project_iot_device` | 工地设备对接 |
| 企业 | `c_corp_basic_info`、`c_project_corp_info` | 参建单位 |

## 与业务侧的衔接点

| 业务字段 | 含义 |
|---|---|
| `t_project_info.DATA_ENGINEERING_ID` | 对应数据中心的工程 |
| `t_project_info.DATA_PROJECT_MASTER_ID` | 对应数据中心的项目 |
| `t_project_info.SOURCE` | 3=ZHGD 同步 / 4=YTH 同步 |
| `t_clue_business.CREATE_TYPE` | 2=自动化创建（数据中心推荐来的） |

> 排查"这个工程哪来的"：看 `SOURCE` + `DATA_*_ID` 有没有值。

## 常见问题

- **Q：线索突然多了很多？** 数据中心批量推荐 + 自动审核通过，会批量创建线索（`CREATE_TYPE=2`）。
- **Q：同一个工程出现两次？** 合并表没跑到，或来源不同没被识别为同一工程（看 `t_data_engineering_merge`）。
- **Q：数据中心有工程，业务侧搜不到？** 数据还在 `c_*`/`t_data_*`，没被推荐或没被认领。
- **Q：推荐了但销售没收到？** 看 `c_recommend_record` 的状态和接收人。
- **Q：外部数据更新了，业务侧不跟变？** 设计如此——业务侧是**快照**，通过 `DATA_*_ID` 关联，不自动同步。
