# 线索全生命周期（线索池 → 分配 → 跟进 → 转化 / 回收）

> 归属：`crm-flow` · docKey：`crm/flow/lead-lifecycle` · 证据基线：zhgj-crm-server（2026-11）

## 一句话

线索是 LTC 的入口资产，**不属于任何销售，属于"池"**。它被创建后进入线索池，由规则分配给销售（或销售自己领取），在保护期内必须跟进；跟进推动它转化为商机，超期未转化则被系统回收回池。整条链路由**日更定时任务 + 状态机 + 流转记录**三件事驱动。

## 全景流程

```
创建(3种来源) → 线索池(未分配) → 分配/领取 → 私海(已分配,开始计保护期)
                                              │
                        ┌─────────────────────┼─────────────────────┐
                        ▼                     ▼                     ▼
                    跟进/编辑/转移        转化成功(→商机)        超时未转化
                    (不动阶梯)            progressType=21      系统回收(→线索池)
                                                                clueStatus=2
```

## 两套并行的状态，别混

线索身上同时有**两个状态维度**，问"线索是什么状态"必须说清问的是哪个：

| 维度 | 字段 | 取值 | 含义 |
|---|---|---|---|
| 业务状态 | `t_clue.CLUE_STATUS` | 0 有效 / 1 转化失败 / 2 超时回收 | 这条线索"还活着吗" |
| 链路阶梯 | 流转记录 `FlowType.progressType` | 0 池 → 1 已分配 → 9 回收 → 21 转商机 → 24 已报价 → 25 已成单 → 26/27 失单 | 这条线索"走到哪一步了" |

`CLUE_STATUS` 只有三个值，看的是**生存状态**；`progressType` 是一串值，看的是**销售进程**。一条线索可以是"有效(0) 且 已报价(24)"，也可以是"超时回收(2) 且 停在已分配(1)"。

## 数据模型：t_clue 关键字段

| 字段 | 含义 | 业务作用 |
|---|---|---|
| `CLUE_ID` / `CLUE_CODE` | 主键 / 线索编号 | 编号是业务单号，对外沟通用它 |
| `CLUE_SOURCE` | 线索来源（字典） | 来源分析、渠道 ROI 的分母 |
| `CUSTOMER_TYPE` / `CUSTOMER_ID` / `CUSTOMER_NAME` | 客户类型 / 客户 ID / 名称 | 个人客户 or 企业客户 |
| `PROJECT_MASTER_ID` / `PROJECT_MASTER_NAME` | 关联工程项目 | 工程类线索的落点 |
| `INTENTION_LEVEL_ID` | 意向等级 | 优先级排序、分配权重 |
| `AREA_CODE` / `ADDRESS` / `LNG` / `LAT` | 区域 / 地址 / 经纬度 | **分配规则的唯一依据**（按区域找人） |
| `DEPARTMENT_ID` / `USER_ID` / `NICKNAME` | 归属部门 / 归属销售 / 销售名 | 分配后写入，`USER_ID=0` 表示在池里 |
| `ALLOCATE_TIME` / `ALLOCATE_NUMBER` | 分配时间 / 分配次数 | 保护期起算点；次数用于识别"烫手线索" |
| `CLUE_STATUS` | 0/1/2 | 见上表 |
| `IS_TRANSFORM` | 是否已转化 | 快速判断，避免联表查商机 |
| `LINKMAN` / `PHONE` / `GENDER` | 联系人 / 电话 / 性别 | 查重的主键之一 |
| `CREATE_USER_ID` | 创建人 | 区分"自建"还是"系统采集" |

附属表：

| 表 | 作用 |
|---|---|
| `t_clue_allocate_record` | 分配/领取/转移流水（谁在什么时候把线索给了谁） |
| `t_clue_fail_record` | 转化失败记录（失败原因，做失单分析） |
| `t_clue_follow_record` | 跟进记录（跟进方式、内容、时间） |
| `t_clue_file` | 线索附件（报价单、图纸等） |
| `t_clue_business` | 转化后的商机 |

## 动作 1 · 创建（三种来源）

同一个"新建"动作按**操作人身份**拆成三种 `FlowType`，目的是让流转记录能区分线索归属来源，直接影响后续分配规则和业绩归属：

| FlowType | 来源 | 场景 | 流转描述 |
|---|---|---|---|
| `SYSTEM_ZERO` | 系统自动创建 | 数据采集/外部导入自动生成 | "系统自动创建" |
| `SALES_ZERO` | 销售创建 | 销售手动给自己建线索 | "{}手动给自己创建线索" |
| `ZERO` | 非销售创建 | 其他角色（市场/客服/管理员）建的线索 | "{}手动创建线索" |

接口：`POST /app/clue/add`（`ClueController.java:52`）。创建时是否自动分配，取决于区域下有没有启用状态的营销人员。

## 动作 2 · 分配（规则引擎，不是手工拍脑袋）

分配逻辑集中在 `AllocateClueRuleArea.allocate()`，规则参数存在系统设置里（不是硬编码）：

1. **按区域找人**：取线索的 `AREA_CODE`，向上递归出**当前区域 + 所有父区域**（`selectParentAreaCode`），再查这些区域下**启用状态**的营销人员（`listUserArea`）。
2. **只有 1 个人 → 直接给他**，不参与权重计算。
3. **多个人 → 按权重分配**，权重策略由 `CLUE_SAME_AREA_ALLOCATE_RULE` 配置：
   - 策略 1：**线索少优先**（负荷均衡，谁手上线索少给谁）；
   - 另一策略：**转化率高优先**（前端线索分配页的"转化率分配"选项）。
4. **平均分配缓存**：Redis key `clue_average_allocate_key:`，用于轮询式均分的游标，避免每次都从第一个人开始。

分配后写入 `USER_ID` / `DEPARTMENT_ID` / `NICKNAME` / `ALLOCATE_TIME`，`ALLOCATE_NUMBER + 1`，并产生 `FlowType=1（分配）` 的流转记录（系统分配 `SYSTEM_ONE` / 手动分配 `ONE`）。

**区域找不到人就不分配**——线索会一直躺在池里，这是"线索没人领"的最常见原因，不是 bug。

## 动作 3 · 领取 / 转移 / 编辑 / 删除

| 动作 | Service 方法 | 改什么 | 流转 |
|---|---|---|---|
| 领取 | `drawDown` | 把池里的线索挂到自己名下 | `FlowType=2 领取` |
| 转移 | `transfer` / `batchTransferClue` | 改 `USER_ID` 到另一个人 | `FlowType=3 转移` |
| 编辑 | `edit` | 业务字段（不动归属） | `FlowType=4 编辑` |
| 删除 | `delete` | 逻辑删除 `IS_DELETE=1` | 不留流转 |
| 批量 | `batchAllocateClue` / `batchAllocateOrTransferClue` | 批量分配或转移 | 逐条生成流转 |

批量接口是**逐条处理**的：一条失败不影响其他条，但也没有整体事务，调用方要看返回的失败清单。

## 动作 4 · 转化（线索 → 商机）

`transform` 是链路的分水岭：

1. 创建 `t_clue_business`（商机），状态落 **1 初步意向**；
2. 线索 `IS_TRANSFORM` 置为已转化；
3. 写 `FlowType=21（已转商机）`，阶梯升到 **21**；
4. 此后线索的阶梯随商机推进同步升（23 销售方案 / 24 已报价 / 25 已成单），**线索自己不再单独变更状态**。

转化失败则写 `t_clue_fail_record` + `CLUE_STATUS=1`。

## 动作 5 · 回收（规则驱动，代码在定时任务里）

**回收不是业务代码触发的**，这是排查时最容易走错方向的地方。实现在 `zhgj-scheduleTask`：

| 任务 | 方法 | 作用 |
|---|---|---|
| 线索自动分配日报 | `newClueAllocation(checkDate)` | 统计待分配/今日分配/今日超时回收数，推送日报 |
| 回收提前提醒 | `overTimeAdvanceReminder` | 按配置的**提前 N 天**提醒（`reminderDayList` 逗号串） |
| 超时提醒 | `overTimeReminder` | 保护期剩余天数 = `restrictTime - 已过天数`，命中提醒日则通知 |
| 从未跟进汇总 | `neverTrackedSummaryReminder` | 分配后一次都没跟进的线索，汇总提醒主管 |

保护期天数（`restrictTime`）和提醒天数都来自系统设置 `getClueExpireParams()`，**改规则不用改代码，改配置即可**。超时后由系统回收：`CLUE_STATUS=2`、`USER_ID` 清零回池、`FlowType=SYSTEM_NINE（系统回收）`、阶梯落 9。

## 动作 6 · 查重与参数校验

- `repeatInfo`：查重，返回可能重复的线索。判重维度是**联系人 + 电话**（`LINKMAN` / `PHONE`），不是客户名。
- `checkClueParams`：创建/编辑前的参数校验（必填、格式、越权字段）。
- `check`：单条校验接口，供前端即时提示。

查重是**提示性**的，不强制拦截——允许销售在明知重复的情况下继续建，但会留痕。

## 状态与阶梯怎么更新（updateFlowProgressType）

所有动作最后都调 `updateFlowProgressType` 统一推进阶梯。规则：

- 有认领但没转商机 → 一律算 **1 已分配**；
- 已转商机但没到报价/合同 → 算 **21 已转商机**；
- 报价后 → **24**；成单 → **25**；失单 → **26/27**。

因此**阶梯是"推导值"而不是"存量字段"**，统计时按阶梯聚合比按 `CLUE_STATUS` 聚合更贴近业务。

## 权限与可见范围

线索列表必须走 `checkUserCacheParams`（`BasicController.java:166-235`）：

- 销售：只看自己名下；
- 主管：看本部门及下级；
- 管理员：全部。

**漏调这个方法 = 越权**，销售能看到全公司线索。判断"为什么张三看不到某条线索"时，先查归属 `USER_ID` 和部门树，再查权限类型。

## 陷阱与注意事项

1. **回收看定时任务，不看 Service**：`SYSTEM_NINE` 来自 `ClueRecyclingScheduleServiceImpl`，且受系统设置开关控制（`status=1` 才跑）。
2. **区域没人就永远不分配**：`listUserArea` 返回空则 `allocate` 直接 return，线索卡在池里。
3. **保护期是配置项**：`restrictTime` 改了，历史线索的剩余天数会立刻跟着变。
4. **`ALLOCATE_NUMBER` 是质量信号**：被反复分配说明这条线索没人要，做线索质量分析时有用。
5. **查重不拦截**：重复线索会进库，报表去重不能依赖创建时拦截。
6. **状态是魔法数字**：SQL 里直接写 `0/1/2`，改枚举要全局搜。

## 常见问题

- **Q：线索获取有哪三种创建来源？** 系统自动创建（`SYSTEM_ZERO`）、销售创建（`SALES_ZERO`）、非销售创建（`ZERO`），靠 `FlowType` 区分。
- **Q：线索为什么一直没分配？** 区域（含父区域）下没有启用的营销人员，`allocate` 直接返回。
- **Q：线索怎么回池的？** 定时任务判定保护期超时，系统回收：状态置 2、归属清空、阶梯落 9。
- **Q：线索状态有哪些？** 业务状态只有 0/1/2；完整进度要看 `progressType` 阶梯。
