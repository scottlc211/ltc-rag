# 商机：阶段推进、撞单判定与失单

> 归属：`crm-flow` · docKey：`crm/flow/lead-to-opportunity` · 证据：`t_clue_business` DDL + `BusinessRepeatServiceImpl` + `ProjectInfoServiceImpl:2593` + `BusinessController`

## 一句话

商机是**线索转化后的销售过程载体**：一条线索只能转化出一个商机，商机走完「初步意向 → 需求沟通 → 销售方案 → 销售报价 → 销售合同」五个阶段，任何阶段都可能失单。转化和保存时都要过**撞单判定**，这道门决定一条商机能不能存在。

## 角色与入口

| 角色 | 端 | 入口 | 能做什么 |
|---|---|---|---|
| 销售 | app | `/app/business` | 创建、编辑、切换阶段、转移、失单 |
| 销售主管 | web | 商机列表 | 批量转移、回收统计 |
| 系统 | 内部 | `BusinessRepeatServiceImpl` | 保存前自动查重/撞单 |

## 状态机（`BUSINESS_STATUS`）

| 值 | 状态 | 推进方式 | 说明 |
|---:|---|---|---|
| 1 | 初步意向 | 转化生成 | 默认落点，商机诞生的地方 |
| 2 | 需求沟通 | 销售手动切换 | |
| 3 | 销售方案 | 销售手动切换 | 关联 `t_clue_business_scheme` 方案表 |
| 4 | 销售报价 | 销售手动切换 | 有报价单后进入 |
| 5 | 销售合同 | 合同创建后 | 商机的终点（不是失单） |
| 6 | 失单 | `lostBusiness` | **终态**，要填 `REASON` |

**推进方式**：`POST /app/business/switchingPhase`，只有这一个人工入口，不存在自动跳阶段。跳过中间阶段是允许的（比如直接从 1 到 4），但**不能从失单回到前面**。

**与线索阶梯的关系**：商机状态变化会反写线索的 `progressType`（21 转商机 → 24 已报价 → 25 已成单）。线索自身不再改状态，只跟随。

## 转化前置条件（两个都必须满足）

线索转商机时校验（`ClueServiceImpl.transform`）：

1. **无撞单**——撞单判定通过；
2. **至少一次有效跟进**——`t_clue_follow_record` 里有记录。

任一不满足就转不了。这是新人最常见的"为什么转化按钮点不动"的原因。

## 撞单判定：三层规则

撞单不是单一开关，是三层叠加，最终结果落在 `t_clue_business_repeat.REPEAT_TYPE`：

| REPEAT_TYPE | 类型 | 触发条件 | 判定依据 |
|---:|---|---|---|
| 1 | 查重规则 | 按配置的字段比对，命中已有商机 | `BusinessRepeatSetting.repeatTrigger`（字段名 → 匹配方式） |
| 2 | 撞单规则-保护期 | 工程处于**保护期** | `t_project_info` 的保护锁定状态 |
| 3 | 撞单规则-锁定期 | 工程处于**锁定期** | 保护锁定状态 |

### 判定流程（`ProjectInfoServiceImpl:2593`）

```
checkProjectCollision(projectMasterId, userId)
  → 返回 protectionLock（1 保护期 / 2 锁定期）和 count
  → protectionLock = 1 → repeatType = 2（保护期）
  → protectionLock = 2 → repeatType = 3（锁定期）
  → 读系统设置 businessCollisionRule：
      值 = 1 → 允许保存
      值 ≠ 1 → count > 0 时不允许保存
```

### 查重是"可配置字段"的

`checkBusinessRepeatInfo` 用**反射**从 `t_clue_business` 上取配置的字段值（`repeatSetting.getRepeatTrigger()`），并支持"字段为空则不参与比对"。这意味着：

- 查重维度不是写死的（可能配的是客户名、电话、项目名）；
- 改了查重配置，**只影响新数据**，历史数据不会重算。

### 撞单关系是双向写的

`saveBusinessRepeat` 会插两条记录（A→B 和 B→A），并把双方的 `IS_REPEAT` 置 1。所以查"谁和我撞了"两个方向都能查到，但**统计撞单数时必须去重**，否则会翻倍。

## 数据模型

### 主表 `t_clue_business`（商机表）

| 字段 | 类型 | 含义 | 业务作用 |
|---|---|---|---|

| `AREA_CODE` / `ADDRESS` / `LNG` / `LAT` | — | 地区与定位 | 区域分析 |

### 撞单关系 `t_clue_business_repeat`

`BUSINESS_ID` + `TARGET_BUSINESS_ID` 唯一索引，`REPEAT_TYPE` 见上表。**这张表是撞单的唯一事实源**，商机上的 `IS_REPEAT` 只是冗余标记。

### 方案 `t_clue_business_scheme`

阶段 3（销售方案）的落地：`SCHEME_DATE`、`SCHEME_TIME`、`USER_ID`、`DEPARTMENT_ID`，一个商机可有多条方案。

## 核心调用链

```
POST /app/business/add
  → 组装 TClueBusiness
  → BusinessRepeatServiceImpl.checkBusinessRepeatInfo()
      → selectRepeatSetting()            // 读查重/撞单配置
      → selectRepeatByBusinessParams()   // 按配置字段查重
      → projectInfoService.checkProjectCollisionInfo()  // 保护期/锁定期
      → 返回 repeatSaveData: 1 允许 / 0 禁止
  → 禁止则直接返回错误，不落库
  → 允许则 insert t_clue_business
  → saveBusinessRepeat()                 // 双向写 t_clue_business_repeat + 置 IS_REPEAT
```

## 失单与回收

`lostBusiness` 做三件事：状态置 6、写 `REASON`、记录当时归属的 `USER_ID`/`DEPARTMENT_ID`。

失单后**不自动回线索池**——回线索池是线索回收定时任务的职责（见《线索全生命周期》）。所以"商机失单了线索还在我名下"是正常现象，直到保护期结束被回收。

## 权限

商机列表同样走 `checkUserCacheParams`：销售只看自己名下，主管看本部门及下级。转移和批量转移需要额外权限。

## 常见问题

- **Q：转化按钮点不动？** 两个前置条件：撞单未通过，或没有至少一次有效跟进。
- **Q：保存商机时报"撞单"？** 工程处于保护期或锁定期，且 `businessCollisionRule ≠ 1`（不允许保存）。
- **Q：撞单数统计为什么翻倍？** `t_clue_business_repeat` 是双向存的，统计要按 `BUSINESS_ID` 去重。
- **Q：成单几率怎么存？** `ODDS` 是万分数，60% 存 6000。
- **Q：商机金额单位？** `MONEY` 注释写明是**元**（合同 `TAX_TOTAL` 未写单位，两者不要混）。
