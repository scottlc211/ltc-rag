# 台账与业绩：月度关账、业绩归属、激励核算

> 归属：`crm-flow` · docKey：`crm/flow/ledger-performance` · 证据：`t_sales_performance_*` / `t_process_result` DDL + management/ledger + management/sales

## 一句话

**台账和业绩不是一回事**，这是最容易搞混的地方：

- **台账**是「查询视图」——实时从合同、回款、发货里聚合出来，**没有自己的表**，改一条合同台账立刻变；
- **业绩**是「关账快照」——按**月度关账**固化下来，关账后原数据再变业绩也不变，除非反关账重算。

搞不清这个区别，就会问出"合同金额改了，为什么我业绩没变"。

## 台账 vs 业绩

| 维度 | 台账 | 业绩 |
|---|---|---|
| 数据来源 | 实时查合同/回款/发货 | 关账时快照落表 |
| 是否可改历史 | 跟着源数据变 | 关账后锁定 |
| 主表 | **无**（`LedgerController` 直接查） | `t_sales_performance_info` |
| 时间粒度 | 任意区间 | 年/季/月 |
| 谁维护 | 系统自动 | 财务/销售助理关账 |

## 业绩归属链（谁的单子算谁的）

```
t_process_result（审批结果表）
   ├── SALES_USER_ID      审批关联销售用户ID  ← 业绩归属的核心
   ├── APPLY_PERSON_ID    发起人
   ├── RELATION_ID        关联单据主键（合同/报价/发货的 ID）
   ├── PROCESS_CONF_TYPE  1报价 2合同 3超额报价 11用印
   ├── RESULT_STATUS      0待审批 1通过 2不通过 4撤回
   ├── APPLY_DATE         int 型，如 20251212
   └── REDULT_TIME        审批结束时间（**库里就是 REDULT 这个拼写**）
```

归属规则（按业务类型分叉）：

| 业务类型 | 业绩算给谁 |
|---|---|
| 直营（销售合同） | 线索的 `USER_ID`（谁跟的线索算谁） |
| 代理商 / 备货 | 合同的 `USER_ID`（谁签的合同算谁） |

> 这条差异很关键：直营看**线索归属**，代理看**合同归属**。人员一调动，两种口径的结果可能不一样。

## 关账机制（业绩的核心）

### 业绩主表 `t_sales_performance_info`

| 字段 | 含义 |
|---|---|
| `YEAR` / `QUARTER` / `MONTH` | 年月粒度（月是 01-12 两位） |
| `CLOSING_STATUS` | **0 未关账 / 1 已关账** |
| `REMARK` | 关账备注 |

一个年月一条主记录，关账就是把它置 1。

### 关账记录 `t_sales_performance_record`

| 字段 | 含义 |
|---|---|
| `RECORD_TYPE` | **1 关账 / 2 反关账** |
| `ACCOUNTING_STATUS` | 0 核算中 / 1 已核算 |
| `ACCOUNTING_TIME` | 核算完成时间 |
| `IS_VALID` | 0 无效 / 1 有效（反关账后老记录置无效） |

**关账是异步的**：置位后进入"核算中"，算完才变"已核算"。所以刚关账时业绩可能是空的或半成品，别急着报错。

### 试算表 `t_sales_performance_tmp`

关账前先在 `t_sales_performance_tmp` 里试算（还有 `_tmp_incentive`、`_tmp_incentive_extend`），确认无误再正式关账。**排查"业绩算错了"先看试算表**，不会影响正式数据。

## 激励与提成

| 表 | 作用 |
|---|---|
| `t_sales_performance_incentive` | 销售业绩**价格激励**信息（27 字段，颗粒度到产品/价格区间） |
| `t_sales_performance_incentive_extend` | 激励扩展信息（19 字段） |
| `t_sales_commission` | 提成方案主表 |
| `t_sales_commission_gradient` | 提成**梯度**（阶梯比例） |
| `t_sales_commission_incentive` | 提成激励信息 |
| `t_sales_performance_payment` | 绩效发放登记 |

**提成算法 = 方案（比例/梯度）× 业绩基数**。梯度表决定"超额部分按更高比例"这类规则。

## 销售计划

| 表 | 用途 |
|---|---|
| `t_sales_dept_plan` | 部门销售计划分解（14 字段） |
| `t_sales_employee_plan` | 员工销售计划分解（16 字段） |

达成率 = 实际业绩 / 计划目标。**分母取哪个字段决定达成率高低**——这是历史遗留的 ⚠️ 待确认项。

## 指标口径的两个陷阱

1. **看板与业绩报表用的日期字段不同**：
   - `DataBoardMapper.revenueOverview`（L4–79）和 `performanceStatistics`（L81–149）取的不是同一个时间列（一个是审批结束时间，一个是签约时间）。
   - 两个页面的数对不上**是正常的**，先确认口径再判断对错。

2. **转化率封顶 100%**：`BusinessMapServiceImpl`（L52–76）算四个转化率时做了上限截断，超过 100 显示 100。所以看到"转化率正好 100%"要怀疑是截断而不是真实值。

## 接口

`management/ledger` 下 6 个 Controller：`LedgerController`（主台账）、`AgentLedgerController`、`AgreementLedgerController`、`CompanyLedgerController`、`BusinessStatisticsController`、`InsightController`。

## 核心流程

```
月末关账
  → 建 t_sales_performance_info（YEAR/QUARTER/MONTH，CLOSING_STATUS=0）
  → 试算 t_sales_performance_tmp
  → 确认后置 CLOSING_STATUS=1
  → 异步核算 → t_sales_performance_record（RECORD_TYPE=1，ACCOUNTING_STATUS 0→1）
  → 生成激励 t_sales_performance_incentive → 按 t_sales_commission 算提成
  → 发放登记 t_sales_performance_payment

发现问题需重算
  → 反关账（RECORD_TYPE=2，老记录 IS_VALID=0）→ 重走一遍
```

## 常见问题

- **Q：合同金额改了，业绩没变？** 该月已关账，业绩是快照。要变得反关账重算。
- **Q：业绩为什么是空的？** 刚关账，还在"核算中"（`ACCOUNTING_STATUS=0`）。
- **Q：两个人看到同一单业绩归属不同？** 直营看线索归属、代理看合同归属，口径不同。
- **Q：台账数据能和业绩对上吗？** 不一定。台账实时、业绩快照，跨月对比必然有差。
- **Q：`REDULT_TIME` 是不是拼错了？** 库里就是 `REDULT`，查数据时别写成 `RESULT_TIME`。

## 待确认（⚠️）

1. 达成率的**分母**（年度目标/月度目标/累计目标）。
2. 价格激励的具体分档规则（`t_sales_performance_incentive` 27 个字段的业务含义需业务确认）。
3. 反关账后提成是否自动重算，还是需要重新发放登记。
