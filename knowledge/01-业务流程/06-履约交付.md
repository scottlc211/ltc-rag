# 履约交付：发货单 → 订单 → 子订单 → 安装

> 归属：`crm-flow` · docKey：`crm/flow/order-to-delivery` · 证据：`t_goods_deliver` / `t_goods_order` / `t_goods_sub_order` / `t_goods_sub_install` DDL + management/goods 13 个 Controller（118 接口）

## 一句话

合同审批通过后进入履约。履约**不是一张表能讲清的**：它是**四层结构**——发货单（业务视角的一次发货申请）→ 订单（系统视角）→ 子订单（**按仓库/供应商拆出来的执行单元**）→ 明细。不理解这个四层，就会问出"为什么发一次货有三个订单号"。

## 四层结构（最重要的一节）

```
发货单 t_goods_deliver（1 张，销售发起，走审批）
   └── 订单 t_goods_order（1 个，审批通过生成，带 ORDER_CODE）
         └── 子订单 t_goods_sub_order（N 个，按仓库/供应商/产品类别拆）
               ├── 明细 t_goods_sub_order_detail（发什么、发多少）
               └── 安装 t_goods_sub_install（需安装的才有）
```

**为什么拆子订单**：一次发货里可能既有仓库现货、又有向供应商采购的货。仓库能发的走仓库出库，仓库没有的走供应商直发。两者的执行人、单据、结算完全不同，所以在订单下面再拆一层。

| 子订单 `DELIVER_TYPE` | 含义 | 谁执行 |
|---:|---|---|
| 1 | 仓库出库 | 仓库管理员 |
| 2 | 供应商发货 | 供应商 |

同时子订单还按产品类别再拆（`SUB_ORDER_PRODUCT_CATEGORY`）：

| 值 | 类型 | 说明 |
|---:|---|---|
| 1 | 硬件 | 有实物、要发物流 |
| 2 | 软件（需 SN） | 有 SN 码，不发达物流 |
| 9 | 其他（不含 SN 的软件与服务） | 只交付不发货 |

所以**"一个订单几个子订单" = 发货方式种数 × 产品类别数**。

## 三个状态机

### 发货单 `DELIVER_STATUS`

| 值 | 状态 | 说明 |
|---:|---|---|
| -1 | 草稿 | 销售建单默认 |
| 0 | 待审批 | 提交后 |
| 1 | 审批通过 | **触发订单生成** |
| 2 | 审批不通过 | 可改再提 |
| 4 | 撤回 | |
| 5 | 作废 | 终态 |
| 11 | 待发货 | 订单已生成、货还没出 |
| 12 | 已发货 | 已出库/供应商已发 |
| 13 | 已收货 | 客户签收 |

### 订单 `ORDER_STATUS`

`5 作废 / 11 待发货 / 12 已发货 / 13 已收货 / **14 部分发货**`

> **14 部分发货**是关键：一批货没发全（比如 10 台只发了 6 台），订单挂在 14 而不是 12。做"待发货"统计时 **11 和 14 都要算**。

### 子订单 `SUB_ORDER_STATUS`

`5 作废 / 11 待发货 / 12 已发货 / 13 已收货 / **21 已退货**`

子订单有退货状态，订单没有——**退货发生在子订单层级**。

## 业务流程

```
[销售] 合同审批通过 → 申请发货（建发货单，填收货信息）
                       ↓
[审批] 发货审批 → 通过
                       ↓
[系统] 生成订单 t_goods_order（ORDER_STATUS = 11）
        按「发货方式 × 产品类别」拆子订单
                       ↓
[仓库] 仓库出库（子订单 DELIVER_TYPE=1）：扣库存、记 SN、填快递单
[供应商] 供应商发货（DELIVER_TYPE=2）：走采购流程（普通采购/供应商直发）
                       ↓
[客户] 签收 → 上传签字附件 → 子订单 13 已收货
                       ↓
[安装] 需安装的生成子安装单 → 安装公司派单 → 安装完成上传签字
```

### 发货可多批次

一张合同的货可以**分多次发**（业务流程图明确写了"发货申请可多批次"）。每次发货是一张新的 `t_goods_deliver`，所以：

- `t_goods_deliver` 与 `t_clue_contract` 是**多对一**；
- 合同上的 `EXECUTED_*` 系列字段就是各批次累计回写的；
- 合同 `CONTRACT_STATUS` 到 13（履约中）是首批发货，到 14（履约完成）是全部发完。

### 订单 `t_goods_order` / 明细

`ORDER_CODE`、`GOODS_DELIVER_ID`、`ORDER_STATUS`、`ORDER_TIME`。
明细 `t_goods_order_detail`：`PRODUCT_NUMBER`（总待发）+ `DELIVERD_NUMBER`（已发），**剩余可发 = 两者之差**。

### 子订单 `t_goods_sub_order`

| 字段 | 含义 | 关键点 |
|---|---|---|
| `SUB_ORDER_CODE` | 次订单号 | **客户实际看到的单号** |
| `DELIVER_TYPE` | 1 仓库出库 / 2 供应商发货 | 决定执行方 |
| `SUPPLIER_ID` / `WAREHOUSE_ID` | 供应商 / 仓库 | 拆单依据 |
| `SUB_ORDER_STATUS` | 见状态机 | 含 21 已退货 |
| `SUB_ORDER_PRODUCT_CATEGORY` | 1 硬件 / 2 软件需SN / 9 其他 | 拆单依据 |
| `EXPRESS_NO` | 快递单号（2000 字符，可多个） | |
| `SIGN_FILE_URL` / `SIGN_DESC` | 签字附件 / 说明 | 收货凭证 |

### 子安装 `t_goods_sub_install`

`SUB_INSTALL_STATUS` **0 待安装 / 1 已安装**；`SUPPLIER_ID` 是**安装公司**（企业库）；
`IS_CHARGE` 0 不付费 / 1 付费，配 `CHARGE_MONEY`（预估）和 `REAL_CHARGE_MONEY`（实际）；
`COMPLETE_TIME`、`REVOKE_TIME`（撤销时间）、签字附件。

### 采购 `t_goods_purchase`

`PURCHASE_TYPE`：**1 普通采购 / 2 供应商直发 / 3 常规采购退货 / 4 供应商直发退货**。
有 `ORDER_ID` / `SUB_ORDER_ID` / `CONTRACT_ID` / `QUOTATION_ID` 四路追溯，明细里 `PURCHASE_NUMBER`（已采）/ `NOT_PURCHASE_NUMBER`（最大可采）/ `RETURN_NUMBER`（已退）。

## 库存与 SN

- 库存扣减点：**仓库出库动作**（不是发货单审批通过时）；
- 需要 SN 的产品（`NEED_SN = 1`）出库时必须绑定 SN 码；
- SN 变更走 `t_goods_inventory_sn_change_record`，**留痕不改历史**；
- 退换货回补库存，走 `t_goods_inventory_detail`。

## 常见问题

- **Q：为什么一次发货有多个订单号？** 拆了子订单，`SUB_ORDER_CODE` 才是客户看的单号，`ORDER_CODE` 是系统主单。
- **Q：订单为什么是"部分发货"？** `DELIVERD_NUMBER < PRODUCT_NUMBER`，货没发全。
- **Q：退货在哪一层做？** 子订单层（`SUB_ORDER_STATUS = 21`），不在订单层。
- **Q：安装费谁出？** `IS_CHARGE`：0 公司承担（含在合同安装费里），1 客户/项目另付，看 `CHARGE_MONEY`。
- **Q：发货单能从草稿直接跳到已发货吗？** 不能，必须走审批（0 → 1）才会生成订单。
