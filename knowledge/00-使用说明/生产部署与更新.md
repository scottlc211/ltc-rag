# 生产部署与文档更新

> 归属：`meta` · docKey：`meta/deploy` · 适用：把 `knowledge/` 推到生产 RAG 服务

## 一句话

**不用一篇篇传**。`scripts/kb_push.py` 一次推完全部 34 篇；以后改了文档，**重跑同一条命令**就行——服务端按 `(namespace, docKey)` 判断，内容没变自动跳过，变了自动升版本。

## 一、生产需要先准备什么

| 前置 | 说明 | 检查方式 |
|---|---|---|
| MySQL 迁移 | 必须跑过 `sql/migrations/004-namespace.sql`（`kb_namespace` 表） | `SELECT * FROM kb_namespace;` |
| 命名空间 | 先建 `ltc`，否则文档进去了但 `namespace=*` 查不到 | `GET /v1/namespaces` |
| Qdrant | 向量库可用 | `GET http://<qdrant>:6333/collections` |
| Embedding 服务 | 嵌入服务可用（bge-small-zh 512 维） | 看 `/v1/health` |
| ADMIN Key | 推送接口要 ADMIN 权限 | 能调 `POST /v1/documents/text` |

> ⚠️ **最容易踩的坑**：命名空间不建就推文档。文档确实入库了，但 `namespace=*` 是从 `kb_namespace` 展开的，没注册的空间等于不可见。

## 二、第一次全量推（一次搞定）

```powershell
$env:LTC_API_KEY = "<生产 ADMIN KEY>"

# 1. 先看会推什么（不写库）
python scripts/kb_push.py --env-check --dry-run --base http://<生产IP>:8081

# 2. 建命名空间 + 全量推
python scripts/kb_push.py --base http://<生产IP>:8081 --ensure-namespace

# 3. 验收：库里应该有 34 篇
curl.exe -s "http://<生产IP>:8081/v1/documents?namespace=ltc&limit=200" -H "X-API-Key: $env:LTC_API_KEY"
```

推送顺序由脚本内的 `MANIFEST` 决定（4 个批次），**不是必须的，但有意义**：

| 批次 | 内容 | 为什么这个顺序 |
|---|---|---|
| 1 | 使用说明、表/字段/接口/枚举/代码地图 | 先让"有什么"可查，后面的文档才有索引支撑 |
| 2 | 业务流程主干 10 篇 | 核心问答内容 |
| 3 | 主数据 / 系统 / 看板 / 数据中台 / 指标 | 支撑域 |
| 4 | **覆盖台账 + 待办清单** | 它们的数字是"最终状态"，最后推才不会过期 |

## 三、以后改了文档怎么更新

**改完直接重跑，不用记推过哪些**：

```powershell
python scripts/kb_push.py --base http://<生产IP>:8081
```

服务端行为（已实测）：

| 情况 | 结果 |
|---|---|
| 内容**没变** | 跳过重建，版本不变（输出 `⏭ 未变化 (v2)`） |
| 内容**变了** | 重建该文档全部块，**版本号 +1**（输出 `✅ ... v3`） |
| 文档**新增** | 新插入，v1 |

> 因为幂等，**可以无脑全量重跑**，不会产生重复文档、不会重复计费嵌入。

只改了一两篇时，可以更省：

```powershell
python scripts/kb_push.py --only crm/flow/contract
python scripts/kb_push.py --only crm/flow/contract --only crm/data/customer
```

## 四、版本与回滚

每次更新 `version` 递增，旧块会被删掉（不保留历史版本）。

**回滚办法**：文档都在 Git 里，`git checkout <旧commit> -- knowledge/...` 后重推同一 `docKey`，版本号继续往上加（比如 v5），内容回到旧版。

> 所以**文档必须进 Git**，这是唯一的回滚手段。

## 五、大体积清单文件怎么处理

这些是"参考手册"，不进向量库（会把库撑大、稀释检索质量），**只放仓库和生产服务器文件目录**：

| 文件 | 大小 | 为什么不推 |
|---|---|---|
| `字段字典-全量.md` | 572 KB | 7014 个字段，推了会淹没业务文档 |
| `接口清单.md` | 217 KB | 1407 个接口，同上 |
| `表结构索引-全量.md` | 30 KB | 纯清单 |
| `枚举字典-全量.md` | 39 KB | 纯清单 |
| `前端页面映射-全量.md` | 125 KB | 逐页面明细 |
| `字段字典-按域/*.md` | 合计 550 KB | 与全量内容重复 |

**这些内容的可检索版本已经入库**：
- 字段 → `crm/meta/fields`（字段速查-高频表，40 张高频表）
- 接口 → `crm/meta/api-guide`（接口速查）
- 页面 → `crm/meta/page-guide`（页面速查）
- 枚举 → `crm/meta/enums`（状态码总表）

确实需要全量入某台环境时：

```powershell
python scripts/kb_push.py --include-large --base http://<生产IP>:8081
```

## 六、改完代码后要重跑什么

文档里有大量机器生成的清单，**改了代码就要重新生成再推**：

| 改了什么 | 重跑脚本 | 影响文档 |
|---|---|---|
| Controller 接口 | `python scripts/kb_api.py` | 接口清单 / 接口速查 |
| 数据库表结构 | `python scripts/kb_schema.py` | 表结构索引 / 字段字典 / 高频表 |
| 前端页面 | `python scripts/kb_page.py` | 页面映射 / 页面速查 |
| 枚举类 | `python scripts/kb_enums.py` | 枚举字典 |
| 定时任务 / 配置项 | `python scripts/kb_inventory.py` | 定时任务清单 / 业务配置项 |

顺序：**先跑生成脚本 → 再全量推**。

## 七、多环境怎么管

| 环境 | base | namespace | key |
|---|---|---|---|
| 本地 | `http://127.0.0.1:8081` | `ltc` | `lc123456` |
| 测试 | `http://<test>:8081` | `ltc` | 测试 ADMIN key |
| 生产 | `http://<prod>:8081` | `ltc` | 生产 ADMIN key |

**同一套文档推多个环境，用同一个 `docKey`**，这样三个环境的知识库结构一致，问答结果可比。

## 八、常见错误

| 现象 | 原因 | 处理 |
|---|---|---|
| 推成功但问答查不到 | 命名空间没注册 | `--ensure-namespace` 重推 |
| 401 / 403 | Key 不是 ADMIN | 换 ADMIN key |
| 500 且日志报连接失败 | MySQL 或 Qdrant 不可用 | 先查 `/v1/health` |
| 版本号一直涨但内容没变 | 文件编码/换行变化 | 统一 UTF-8 无 BOM、LF |
| 检索到重复内容 | `docKey` 不一致（同一文档两个 key） | 全库查 `docKey` 去重 |

## 待确认（⚠️）

1. 生产是否与本地同版本（`kb_namespace` 迁移是否已执行）。
2. 生产 embedding 模型维度必须与本地一致（512），否则向量写不进去。
3. 是否需要定时同步（当前是手动推；如需自动化，可在 CI 里跑 `kb_push.py`）。
